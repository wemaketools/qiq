## 2. Executive Summary

This is a **platform migration, not a product change**. QuoteIQ — a multi-tenant insurance Leads and Quotation Intelligence platform (lead intake → workflow-driven lead/quote lifecycle → dashboards, alerts, reports, tenant/user administration, full RBAC and auditability) — is migrated from:

- .NET 10 backend → **TypeScript backend on Vercel serverless functions (Node.js 22 runtime)**, with the `/api/v1` surface served by a **Hono** app inside a catch-all function (Q-3b).
- Self-managed PostgreSQL + Liquibase → **Supabase PostgreSQL** with **plain SQL migrations managed by the Supabase CLI** (`supabase/migrations/`); runtime data access via the **Kysely** type-safe query builder over `pg` (Q-1).
- Hangfire recurring/enqueued jobs → **Supabase Cron** (`pg_cron`, scheduled sweeps defined in SQL migrations) + **Supabase Queues** (`pgmq`, event-driven async work), with the TypeScript job handlers running in secret-protected Vercel endpoints invoked over HTTP via `pg_net`, and documented **local execution paths** (CLI cron-runner scripts, `queue:worker` drain script; `pg_cron`/`pgmq` also run inside the local Supabase stack). This is an explicitly approved deviation from the PRD's Vercel-Cron/Queues example: CLAUDE.md permits an explicitly approved Vercel-compatible alternative, and Supabase Cron/Queues qualify while keeping jobs on the already-adopted platform (Q-7).
- Docker-compose Postgres/MinIO/Vault → **Supabase CLI + Docker local stack** (database, auth, storage). No separate identity container remains: self-hosted Keycloak is replaced by Supabase Auth (below), which runs inside the same Supabase stack — the local stack is Supabase-only and now includes auth.
- Self-hosted Keycloak OIDC → **Supabase Auth** (GoTrue, part of the already-adopted Supabase platform; supersedes an earlier in-session Clerk decision). Supabase Auth provides authentication and identity; the application's own RBAC model remains the authorization source of truth. Local development authenticates against the local Supabase Auth service in the Docker stack — offline, with no external hosted identity dependency.

**Preserved unchanged (behavior parity is the acceptance bar):** the domain model (Lead before Quote; every Quote belongs to exactly one Lead), tenant isolation enforced server-side, the RBAC model (permissions, roles, groups, direct assignments, per-tenant context, effective-permission union, Internal/global users), the workflow-operation lifecycle with append-only status history, all five dashboards + Alerts center + Reports, tenant-configurable reference data with guarded statuses, Tenant Manager and User Manager, auditability, and the **existing `/api/v1` API contract** so the React frontend migrates with minimal changes.

The migration is complete when no .NET or Hangfire runtime is required, the TypeScript backend deploys to Vercel against Supabase Postgres, local development runs from a clean checkout via documented commands, and the existing product capabilities (validated by the existing e2e suite, adapted to the new stack) all pass.

## 3. Goals and Non-Goals

### 3.1 Goals (PRD §2)

- G-1: All backend application logic in TypeScript (strict mode), deployable to Vercel with no persistent server process.
- G-2: Supabase Postgres as the operational system of record; serverless-safe connection strategy (transaction pooler) for runtime traffic.
- G-3: Reproducible local development: Supabase CLI + Docker, source-controlled SQL migrations, repeatable seed data, documented scripts, `.env.example`, no cloud dependency for the daily workflow.
- G-4: Every Hangfire job replaced by a Supabase Cron (`pg_cron`) or Supabase Queues (`pgmq`) pattern with a working local execution path, durable `job_run` history, idempotency, and retry tolerance.
- G-5: Behavior parity: same user-facing features, same API contracts where practical, same metric definitions, same alert semantics, same RBAC/tenant-isolation guarantees.
- G-6: Deployment readiness: `vercel.json` (function config; cron scheduling lives in SQL migrations via `pg_cron`, not in `vercel.json`), environment-variable catalog, deployment/local-dev/background-jobs docs, Local/Preview/Staging/Production environment model.
- G-7: CI-validated typecheck, tests, and clean-database migration application.

### 3.2 Non-Goals (PRD §3, §5.2)

- Rewriting or redesigning the frontend UI; replacing the frontend framework (the Vite/React/Redux SPA is preserved).
- Changing the business model, dashboard definitions, metric formulas, or terminology.
- New product features: AI scoring, automated pricing, email/WhatsApp integrations, broker portal, scheduled report distribution (still excluded per the prior product decision — see A-13/Q-14).
- A generic multi-cloud queue abstraction; the target is the approved Supabase Cron/Queues execution model only (the thin app-level queue interface over the pgmq-backed adapter exists solely as a test seam and to keep handler code transport-agnostic).
- Continuing to run/maintain the .NET backend after cutover (no dual-running compatibility layer beyond the migration window).

## 4. Assumptions

Each assumption `[A-n]` was routed to the human reviewer with the open questions; all have now been explicitly confirmed or amended by human decision (see §5 — every question RESOLVED).

- **[A-1] No production data migration.** The current system is a pre-production build whose only data is the repeatable demo seed. The Supabase schema is recreated from the approved domain model (Liquibase changelogs converted to ordered plain-SQL migrations) and the demo dataset is regenerated by the new seed process. The PRD §12 data-migration machinery therefore reduces to schema conversion + seed/metric parity validation, not a dump/restore of live data. The seed process (idempotent baseline catalog seed + demo seed) must be runnable against **both** the local Supabase database and any deployed environment via documented npm scripts/SQL. (Q-8 RESOLVED — confirmed.)
- **[A-2] Frontend stays a Vite React SPA; backend = plain Vercel Functions.** The backend is implemented as Vercel serverless functions (Node.js runtime) in the same Vercel project as the SPA, so the frontend's existing relative `API_BASE_URL = '/api/v1'` keeps working. Next.js is **not** adopted (adopting it would be a frontend-framework change, which is a non-goal). Consistent with the Hono-in-a-Vercel-Function routing decision (A-19/Q-3b). (Q-15 RESOLVED — confirmed.)
- **[A-3] API contract preserved 1:1.** Paths under `/api/v1`, the `X-Tenant-Id` header, RFC 7807 `problem+json` error shapes with structured `errors[]`, DTO field names, pagination (`{items,page,pageSize,total}`, default 25/page), sorting/filtering params, and `availableOperations` payloads are unchanged. Deviations are limited to the attachment transfer pattern (A-7) and the intake auth mechanism (Q-19, replacing Keycloak client-credentials). Frontend changes are limited to build/deploy/env plumbing, the Supabase Auth auth-layer swap (A-4), and the attachment transfer pattern (A-7).
- **[A-4] Supabase Auth is the identity provider.** (Human decision re-resolving Q-4, superseding the earlier in-session Clerk choice; Keycloak already dropped entirely.) Supabase Auth (GoTrue) is part of the Supabase platform this migration already adopts, so no separate identity infrastructure — hosted or containerized — is added anywhere. The SPA authenticates via the Supabase JS client (`@supabase/supabase-js` auth: email/password sign-in, session persistence, and token refresh handled by the client); the backend verifies Supabase-issued access tokens server-side via `@supabase/supabase-js` `auth.getClaims()` against the project's asymmetric JWT signing keys/cached JWKS (see A-10 and Q-2); User Manager provisions/disables users via the **Supabase Auth Admin API** (service-role key, server-side only). Local development authenticates against the **local Supabase Auth service** inside the Supabase Docker stack — offline auth with no external hosted identity dependency and no separate identity container; `supabase start` provisions it and prints the anon and service-role keys for `.env.local`; asymmetric JWT signing keys are enabled on the local stack too (A-10). Supabase Auth provides authentication + identity only — the app's own RBAC (roles/groups/permissions, per-tenant assignments, effective-permission union) remains the authorization source of truth; Supabase Auth is NOT our RBAC. Server-to-server API intake auth remains the approved Q-19 first-party hashed-API-key scheme (Supabase Auth serves interactive end-user sessions, not external M2M intake).
- **[A-5] HashiCorp Vault is dropped; its role is split across a two-tier secrets model (Q-5 RESOLVED — human decision).** Tier 1 — **Vercel Sensitive Environment Variables** hold **static, application-wide/platform (control-plane) secrets** that are the same for all tenants and known at deploy time: `SUPABASE_DATABASE_URL`/`SUPABASE_DIRECT_DATABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`/`INTERNAL_JOB_SECRET` (protecting the pg_net-invoked cron/queue-drain endpoints, Q-7), the Q-19 API-key pepper/signing secret, and any external-service credentials that are global to the app. (`SUPABASE_JWT_SECRET` is no longer in this list: token verification uses `auth.getClaims()` against asymmetric signing keys per A-10, so the legacy JWT secret is not required for verification and is dropped from the catalog; no other consumer needs it.) This is Vercel's write-only, encrypted-at-rest variable type (values cannot be read back through the dashboard or API after being set), configured per environment; locally, git-ignored `.env.local` holds local-only development values for this tier, and browser-safe values remain ordinary (non-sensitive) env vars. Tier 2 — **Supabase Vault** (the `vault` schema — pgsodium-backed secrets encrypted at rest inside Postgres) holds **dynamic, tenant-scoped (data-plane) secrets**: tenant-specific integration credentials, per-customer/per-tenant outbound API keys, OAuth refresh tokens, and integration secrets. These are per-tenant encrypted rows, not env vars: created/rotated at runtime, decrypted only server-side under least privilege, with tenant isolation enforced on every read (one tenant's secrets are never readable by another tenant), never exposed to the browser, never logged, and with access auditable. Both tiers are reachable only through the typed server-side config/secrets module — no ad-hoc access. Note: most of the named Supabase Vault consumers correspond to PRD non-goal integrations (email/WhatsApp, broker portal, external pricing, etc.) and are future scope — Supabase Vault is adopted now as the designated mechanism and pattern, not as license to build those features (Q-23 RESOLVED: no MVP consumer exists, so **no Vault implementation is built in this migration** — no tables, no secrets-module surface; documented pattern only, implemented when the first real consumer is approved). This reverses the prior-era "Vault everywhere" decision because HashiCorp Vault is not Vercel-native and would add unapproved infrastructure; the reversal is human-approved.
- **[A-6] Attachments move to Supabase Storage behind a swappable storage port (Q-6 backend + abstraction RESOLVED — human decision).** The prior `IObjectStorage` seam is preserved as a TypeScript storage-port interface — `StorageAdapter` in `src/server/lib/storage` — defining the operations the app needs (put, get, delete, signed upload/download URL issuance, exists, as applicable). `SupabaseStorageAdapter` is the default implementation (private bucket, tenant-prefixed keys; metadata stays in `quote_attachments`); alternative adapters (e.g., an S3/MinIO-compatible adapter) can be substituted via configuration without changing domain/service code. The abstraction is justified under CLAUDE.md's rule (a real second implementation or a clear test seam) on both counts: swappable real backends and a fake/local adapter for tests. MinIO is dropped; the Supabase local stack provides Storage locally. The transfer mechanism (A-7) was the one remaining storage decision and is now confirmed (Q-22 RESOLVED — signed-URL flow).
- **[A-7] Attachment transfer uses short-lived signed URLs, not API streaming.** Vercel functions cap request/response bodies at ~4.5 MB, below the 10 MB default per-tenant attachment cap. The backend authorizes, validates (type allow-list, size cap), records metadata + audit, then issues a short-lived signed upload/download URL for the private bucket via the `StorageAdapter`. This is the one deliberate API-contract change (upload/download endpoints return a signed-URL envelope instead of streaming bytes); the frontend attachment feature is updated accordingly. (Q-22 RESOLVED — confirmed; 10 MB uploads are required, so capping at 4.5 MB was rejected.)
- **[A-8] Database access = Kysely (type-safe SQL query builder, MIT — not an ORM) over its Postgres dialect with `pg` (node-postgres) as the underlying driver**, through the Supabase transaction pooler (Supavisor, port 6543) for runtime traffic; direct connection (`SUPABASE_DIRECT_DATABASE_URL`) only for migrations/admin scripts. Small per-instance pool (max 1–2), no session-state reliance, transaction-pooling-safe usage (the pg dialect configured with **no named prepared statements**). Migrations remain plain SQL managed by the Supabase CLI — Kysely's migrator is **not** used. The Kysely schema is typed from generated DB types (`supabase gen types` or kysely-codegen, per M-12). (Q-1 RESOLVED — Kysely chosen.)
- **[A-9] Boundary validation = `zod`** schemas per request DTO, mirroring the FluentValidation catalog. (Q-2 RESOLVED — approved.)
- **[A-10] Access-token verification = `@supabase/supabase-js` `auth.getClaims()` with asymmetric JWT signing keys; `jose` is dropped.** Supabase-issued access tokens (JWTs) are verified server-side via supabase-js `auth.getClaims()`. Nuance (recorded per human request): `getClaims()` verifies the JWT locally/offline against the cached JWKS **only when the Supabase project uses asymmetric JWT signing keys** (the ECC/JWKS signing-keys feature); with the legacy HS256 shared secret it falls back to a network round-trip to the Auth server per verification — undesirable on serverless cold starts. **Spec decision: enable asymmetric JWT signing keys on every Supabase project (including the local stack)** so `getClaims()` verifies against the cached JWKS with no per-request network call, cold-start tolerant. Consequence: `SUPABASE_JWT_SECRET` is not required for verification and is removed from the env catalog (nothing else consumes it). (Q-2 RESOLVED — jose dropped in favor of this approach.)
- **[A-11] Test framework = Vitest** for backend unit + integration tests (already used by the UI); Playwright suite in `e2e_tests/` is preserved and re-pointed at the new stack. No new test framework.
- **[A-12] Schema conventions preserved:** numeric `bigint` sequence PKs (no UUIDs), tenant-scoped tables LIST-partitioned on `tenant_id` with composite keys `(tenant_id, id)`, partition-creation SQL function invoked inside the tenant-creation transaction, `numeric(18,2)` money, `jsonb` only for audit/history payloads, per-tenant display currency in `tenant_settings`. All of this is plain PostgreSQL and Supabase-compatible.
- **[A-13] Scheduled reports remain out of scope.** The PRD's example `dispatch-scheduled-reports` cron is **not** implemented; on-demand reports/exports only, per the standing product decision. (Q-14 RESOLVED — confirmed excluded.)
- **[A-14] Queue usage is minimal by design.** The only event-driven async job today is targeted alert re-evaluation after a workflow operation. It moves to **Supabase Queues (`pgmq`)** behind the thin `QueuePublisher/QueueConsumer/JobHandler/JobRunRepository` interfaces from PRD §9.7 — backed by pgmq in both deployed and local environments; unit tests may use the in-memory adapter. The previously planned app-owned Postgres `job_queue` table is superseded by pgmq; the durable `job_run` history table is kept for observability/idempotency. (Q-7 RESOLVED.)
- **[A-15] Job observability = tables + logs, no admin UI.** The Hangfire dashboard is replaced by the `job_run` history table plus the pgmq queue/archive tables, inspectable via the `jobs:status` script and structured logs; no new admin screen is built unless separately requested.
- **[A-16] Excel export via `exceljs`** (MIT) replaces ClosedXML; CSV stays hand-rolled with formula-injection guarding. (Q-9 RESOLVED — `exceljs` approved.)
- **[A-17] Behavioral acceptance = existing e2e suite.** The adapted Playwright suite (login, tenant manager, user manager, lead intake, lead/quote workflow, dashboards ×5, alerts, reports, exports, settings, tenant isolation, RBAC visibility, role-403 sweep, cross-tenant internal mode, demo journey, a11y, visual shell) must pass against the migrated stack with only test-infrastructure changes (base URLs, seed invocation, job triggering hooks).
- **[A-18] One Supabase project per persistent environment (Local/Preview/Staging/Production), plus temporary dev environments via Supabase branching.** Vercel Preview deployments use the shared non-production Preview Supabase project (Q-12); Preview/Staging never touch Production data; the human provisions/owns the hosted projects (provisioning deferred). Only Local must be fully functional at the end of this migration; deployed environments are configured via documented placeholders. (Q-11/Q-12 RESOLVED.)
- **[A-19] HTTP routing = Hono inside a small number of catch-all functions.** To preserve ~100 existing routes without one Vercel function per route (cold-start and function-count cost), the `/api/v1` surface deploys as one catch-all Vercel function (`api/v1/[[...segments]]`) hosting a **Hono** app (MIT micro-router/framework) — Hono handles method + path routing plus middleware for auth, tenant context, and error mapping — alongside dedicated `api/cron/*` and `api/queue/*` endpoints. Still plain Vercel Functions (no Next.js). (Q-3b RESOLVED — Hono chosen over a hand-rolled router.)
- **[A-20] Rate limiting is deferred to platform tooling.** The .NET in-process rate limiter has no effective serverless equivalent; MVP relies on Vercel platform protections (WAF/firewall) plus Supabase Auth's (GoTrue) built-in protections (auth-endpoint rate limiting, brute-force mitigation) for sign-in. No in-app limiter is built. (Q-17 RESOLVED — confirmed.)

- **Q-16 (runtimes/tooling): RESOLVED — Node.js 22 LTS runtime + npm confirmed** (matching the existing UI/e2e projects). Monorepo layout uses npm workspaces (root + `src/ui` + `e2e_tests`).
- **Q-17 (rate limiting): RESOLVED — A-20 confirmed:** no in-app limiter for MVP; defer to Vercel platform protections + Supabase Auth's built-in auth-endpoint protections.
- **Q-18 (sync export size): RESOLVED — sync-with-documented-limit accepted for MVP.** Exports remain synchronous with a documented size limit under the ~4.5 MB Vercel response cap (seed-scale volumes fit); the scale path (queue-generated exports stored to Storage + signed URL) is noted, not built.
- **Q-19 (server-to-server / API-key lead intake): RESOLVED — first-party API-key scheme approved.** The prior design authenticated `POST /intake/leads` with Keycloak client-credentials tokens; Supabase Auth serves interactive end-user sessions and does not natively provide external machine-to-machine intake credentials. Approved scheme: QuoteIQ issues per-credential keys (tenant- and broker-scoped), stores only salted hashes in a hashed-key table (evolving `api_credentials`), and verifies presented keys server-side, preserving the existing reveal-once/regenerate/disable/audit semantics. It has no platform-feature dependency and maps directly onto the existing `api_credentials` admin UX. Note: these intake keys are credentials **we verify** on inbound calls, stored as salted hashes (verify-only, never retrieved), so they do **not** live in Supabase Vault — the A-5 Vault tier (itself deferred per Q-23) is for retrievable/decryptable tenant-scoped secrets, a distinct category.
- **Q-20 (NEXT_PUBLIC_ prefix vs Vite):** **RESOLVED — withdrawn as moot.** This question concerned the human-provided Clerk env variables, whose `NEXT_PUBLIC_` prefix clashed with the Vite build's `VITE_` convention. With the Clerk decision superseded by Supabase Auth (Q-4), those variables are gone entirely; the browser-safe Supabase variables use the clean Vite prefix directly (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` — M-20a), and no prefix reconciliation is needed. The id is retained for traceability.
- **Q-21 (testing/e2e auth strategy under Supabase Auth): RESOLVED — default approved.** The Playwright e2e login strategy goes through Supabase Auth: (a) **seeded local Supabase Auth test users** created during seed (Auth Admin API with the local service-role key), signed in through the SPA sign-in form with known passwords — exercises the real login surface, used for login specs; plus (b) **admin-minted sessions** via the service-role key injected into browser storage for bulk session setup where suite runtime demands it (a real login still covered by a dedicated spec). Tenancy stays in the app's own `tenants`/`user_tenants` model regardless (Supabase Auth is identity only).
- **Q-22 (attachment transfer mechanism under the Vercel body limit): RESOLVED — signed-URL flow confirmed; 10 MB uploads are required, so capping at 4.5 MB was rejected.** Vercel functions cap request/response bodies at ~4.5 MB, below the 10 MB default per-tenant attachment cap, so attachment bytes cannot always pass through the API. Confirmed A-7 approach: uploads/downloads use short-lived signed URLs issued server-side via the `StorageAdapter` directly against the private Supabase Storage bucket (bytes bypass the Vercel function body limit); the backend authorizes, validates (type allow-list, size ≤ per-tenant cap, default 10 MB), records metadata + audit, then issues the signed URL. A-7 stands as the one confirmed, documented API-contract deviation, with the paired frontend update.
- **Q-23 (Supabase Vault MVP scope): RESOLVED — no concrete MVP consumer; implementation deferred.** Supabase Vault remains the **designated future mechanism** for dynamic tenant-scoped secrets (A-5), but **no implementation is built in this migration** — no tables, no secrets-module surface. The named consumers correspond to PRD non-goal integrations, and the Q-19 intake keys are hashed verify-only credentials that explicitly do not belong in Vault. Documented pattern only, to be implemented when the first real consumer is approved.

**Implementation notes (guidance carried into implementation tasks — not open decisions):**

- **`getClaims()` requires asymmetric signing keys for offline verification (A-10/Q-2):** supabase-js auth.getClaims() should perform local JWT verification using the project's asymmetric signing keys and JWKS. All deployed Supabase environments must therefore use asymmetric JWT signing keys. Legacy symmetric HS256 signing would cause getClaims() to rely on remote Auth-server verification rather than local cryptographic verification, adding an avoidable network dependency and latency to authenticated API requests.
- **~~RLS data path vs service-role bypass (Q-10)~~ — WITHDRAWN (2026-07-20).** Moot: RLS is not adopted (Q-10), so there is no policy path to make effective and no app-role hardening to reconcile with the pooler. App-level tenant predicates carry the isolation load by design, not as a fallback.
- **Magic-number/file-content validation under direct-to-storage uploads (A-7/Q-22, R-8):** a post-upload verification step, or an explicit accepted-risk sign-off — flag during implementation, do not drop silently (§16).

## 6. Functional Requirements

Requirements are split into **platform-migration requirements (M-nn)** — the work of this PRD — and **behavior-parity requirements (P-nn)** — the preserved product behavior the migrated platform must still satisfy. Task generation happens after approval; every M/P requirement must map to ≥1 task and ≥1 acceptance criterion.

### 6.1 Platform migration requirements

**Backend (PRD §7)**

- M-01: All backend logic in TypeScript strict mode; no `any`; explicit domain/request/response/persistence types; server-only code excluded from client bundles.
- M-02: API deploys as Vercel functions (Node runtime), stateless, cold-start tolerant, no in-memory state for correctness, idempotent where retried.
- M-03: Modular domain structure under `src/server/domains/` (tenants, users, rbac, leads, quotes, brokers, parties, reference-data, business-rules, assignments, dashboards, alerts, reports, exports, search, intake, api-access, audit) with shared `src/server/lib/` (config, db, auth, tenancy, validation, errors, logging, storage, supabase, router).
- M-04: Shared, reusable request validation (zod schemas per endpoint) at every boundary; typed Result/Error pattern for expected business failures; RFC 7807 responses preserved.
- M-05: Every protected route enforces authentication, effective-permission checks, and (for tenant-scoped routes) tenant-context verification server-side — port of the existing `RequirePermission` + tenant middleware semantics.
- M-06: Audit writes preserved for every privileged/business-critical operation, with tenant context on tenant-scoped events.
- M-07: The full existing `/api/v1` endpoint inventory (see §12) is reimplemented with unchanged contracts, except the attachment signed-URL change (A-7) and the intake auth-mechanism change (Q-19), each of which must be explicitly documented as a contract deviation with any paired frontend/consumer update.

**Database (PRD §8)**

- M-08: Supabase Postgres is the system of record; the schema is recreated from the Liquibase changelogs (`010-foundation` … `170-assignment-slots` + `functions/`) as ordered plain-SQL migrations in `supabase/migrations/`, preserving tables, constraints, indexes, partitioning, and SQL functions (partition-creation helper, etc.).
- M-09: Runtime data access uses the transaction pooler; migrations/admin use the direct connection; no unbounded pools; driver configured transaction-pooling-safe (A-8).
- M-10: Migrations apply cleanly to a fresh local Supabase database (`supabase db reset`) and are validated in CI; risky migrations carry rollback/recovery notes in the migration header comment.
- M-11: Seed data is layered: (1) **baseline seed** — permission catalog + global default reference template, idempotent, applied on every reset and as a deploy step (replaces .NET startup seeding, which has no serverless equivalent); (2) **demo seed** — the full demo dataset (pilot tenant + second tenant, 15+ users across roles, 18 brokers, 200 parties, 300 leads, 500 quotes, 400 follow-ups, 40 pricing approvals, alert-triggering records, plausible history, sample job runs/queued jobs), regenerated as `supabase/seed.sql` and/or `scripts/db/seed.ts`, idempotent (re-run converges), never run automatically in production. Per Q-8, the seed process (baseline + demo) must be runnable against **both** the local Supabase database and any deployed environment via documented npm scripts/SQL.
- M-12: `db:types` generates TypeScript types from the local schema (`supabase gen types typescript --local` or kysely-codegen) to type the Kysely schema used by the data layer (A-8/Q-1).

**Background jobs (PRD §9.6–§9.9, §11) — full design in §9.5**

- M-13: Every Hangfire job is replaced per the §9.5 mapping table; no Hangfire runtime remains.
- M-14: Cron endpoints (`/api/cron/{job}`) are thin wrappers over shared handlers in `src/server/jobs/cron/`, protected by `CRON_SECRET`, **invoked on schedule by Supabase Cron — `pg_cron` jobs defined in SQL migrations calling the endpoints over HTTP via `pg_net`** (Q-7) — idempotent, batch-processing, and record `job_run` rows (start/end/duration/status/error/correlation id/environment/per-tenant counts).
- M-15: Local cron execution path: `cron:list`, `cron:run <job>`, `cron:run:all` scripts invoke the same handlers against local Supabase and write the same `job_run` rows (pg_cron also runs inside the local Supabase stack; the scripts are the documented deterministic local path).
- M-16: Queue work goes through app-level interfaces (`QueuePublisher`, `QueueConsumer`, `JobHandler`, `JobRunRepository`), backed by **Supabase Queues (`pgmq`)** in both deployed and local environments (Q-7); an in-memory adapter exists for unit tests only. Messages carry type, tenant context, correlation ID, idempotency key, minimal payload. Deployed consumption: a `pg_cron` schedule invokes the secret-protected drain endpoint (`/api/queue/drain`) via `pg_net`, which drains the pgmq queue and runs handlers. Local consumption: `npm run queue:worker` polls/drains the same pgmq queue through the same handler code (avoiding container→host networking complexity).
- M-17: Durable job state: pgmq queue/archive tables (enqueue / read-with-visibility-timeout / ack-delete / retry / dead-letter-archive semantics) + the `job_run` history table (+ `job_error`, `job_idempotency_key` where needed); `queue:worker`, `queue:enqueue:test`, `jobs:status` scripts; failed idempotent jobs safely reprocessable.
- M-18: `docs/background-jobs.md` documents every cron name/path/`pg_cron` schedule, queue names/message types, local commands, idempotency expectations, retry/failure behavior, inspection and manual-run procedures per environment, and the explicit description of both consumption paths (deployed: pg_cron → pg_net → Vercel endpoints; local: `cron:run*` scripts + `queue:worker`, with pg_cron/pgmq also present in the local stack).

**Local development (PRD §9, Appendix B)**

- M-19: Clean-checkout local workflow: install deps → `supabase start` → reset/migrate/seed → run backend + SPA locally → run tests — all via documented root package scripts (`dev`, `dev:vercel`, `supabase:start|stop|reset`, `db:migrate`, `db:seed`, `db:types`, `typecheck`, `lint`, `test`, `test:integration`, `cron:*`, `queue:*`, `jobs:status`). Local Supabase is the default database; authentication uses the **local Supabase Auth service** inside the same Supabase Docker stack (`supabase start` provisions it and prints the anon and service-role keys for `.env.local`; asymmetric JWT signing keys enabled per A-10) — fully offline, no external auth dependency, and no separate identity container (the slim Keycloak docker-compose is removed).
- M-20: Environment files: `.env.example` (all variables, placeholders only) and `.env.local.example`; `.gitignore` covers `.env*`, `.vercel`, logs, transient artifacts; browser-safe vs server-only variables explicitly documented; no secrets committed. Tenant-scoped secrets in the A-5 Supabase Vault tier are **database-resident encrypted rows, not `.env`/Vercel entries** — no env-var names exist or are invented for them; only static (platform) secrets appear in the environment-variable catalog. `.env.local` is git-ignored and holds only local Supabase development values (the anon and service-role keys printed by `supabase start` — local-stack values, not real project keys); real keys are never committed.

- M-21: `docs/local-development.md` covers setup, start/stop/reset, job runs, troubleshooting; `docs/environment-variables.md` catalogs every variable (scope, sensitivity — including which are configured as Vercel Sensitive Environment Variables per A-5 — where configured) per the PRD §10.6 table, and notes that tenant-scoped Supabase Vault secrets are database-resident, not environment variables (A-5); `docs/deployment.md` covers Vercel + Supabase setup, migration flow, cron/queue setup, smoke tests, and the PRD §10.8 checklist.

## 7. Non-Functional Requirements

- N-01 **Tenant isolation:** no query path may return another tenant's data; enforced **solely** by the tenant-context layer + repository-level tenant predicates (RLS is not adopted per Q-10, so there is no database-level backstop); integration-tested per endpoint; cross-tenant IDs return 404 (indistinguishable from missing).
- N-02 **Serverless correctness:** no reliance on instance lifetime, in-memory caches for correctness, or exactly-once execution; all handlers retry/duplicate tolerant; long work chunked or queued; job progress durable.
- N-03 **Connection safety:** no connection exhaustion under Vercel concurrency; pooler-compatible driver settings; direct connections only for migrations/admin.
- N-04 **Performance:** dashboard endpoints ≤ 2 s at seed-data volumes through the pooler; list endpoints server-side paginated/sorted/filtered; indexes preserved for tenant/date/status/broker/RM/region/aging/SLA/lost-reason access paths; no N+1 in dashboards/reports.
- N-05 **Auditability, accessibility, theming:** unchanged from the implemented product (WCAG 2.1 AA, design tokens, light/dark).
- N-06 **Determinism/CI:** all tests deterministic, isolated, order-independent, CI-safe; migrations and seed repeatable from clean state.
- N-07 **Licensing/platform:** permissive licenses only; no paid services beyond Vercel + Supabase without approval; no Hangfire/EF Core/Liquibase in the target runtime.
- N-08 **Observability:** structured logs with correlation IDs (requests + jobs), no sensitive data logged; job-run history; migration logs; queue backlog/failure visibility; env-identified job records.
- N-09 **Data retention:** soft deletes preserved (tenants, user deactivation, reference disable, attachment soft-remove); no hard deletes of business records.

Q-23 RESOLVED: no MVP consumer exists, so no Vault-tier implementation is built in this migration (documented pattern only); nothing in the diagram above depends on it.

The .NET tree (`src/api/*`) and all old docker-compose services (Postgres, Keycloak, Vault, MinIO, Liquibase) are removed at the end of the migration (M-13 / Definition of Done) — no slim Keycloak compose survives, since Supabase Auth in the local Supabase stack replaces it (A-4); until cutover they remain the behavioral reference.

### 9.2 Request pipeline

Every API request flows: entry function → Hono app (A-19) → structured-log request context (correlation ID generated or propagated) → Supabase access-token verification (supabase-js `auth.getClaims()` against the cached JWKS — asymmetric signing keys per A-10; no per-request network call) → Hono route resolution → tenant-context resolution for tenant-scoped routes (`X-Tenant-Id` verified against caller memberships or Internal grant; 403 otherwise; intake resolves tenant/broker from the presented API credential per Q-19, never the payload) → permission check (declarative per-route permission requirement) → zod input validation (422 with structured `errors[]`) → domain handler (typed Result) → response mapping (RFC 7807 on failure). Handlers use a per-request `db` handle from the pooled driver; multi-statement business operations run in explicit transactions.

### 9.3 Data access

- `lib/db`: Kysely over its Postgres dialect (`pg` Pool, max 1–2 per instance, no named prepared statements) against `SUPABASE_DATABASE_URL` (pooler); helper for transactions; tenant-scoped query helpers that require an explicit tenant parameter (no ambient global); repository modules per domain built on Kysely's type-safe query builder (raw SQL via Kysely's `sql` template where clearer). Kysely schema typed from generated DB types (M-12).
- Every tenant-scoped SQL statement includes the tenant predicate; a lint/test convention (integration tests per endpoint, N-01) guards regressions since there is no EF global filter equivalent. RLS is **not** adopted (Q-10), so this predicate discipline is the whole of tenant isolation at the data layer — there is no database-level second line of defense behind it.
- Generated DB types (`db:types`) used for row typing where beneficial (M-12).

### 9.4 Serverless adaptations of prior behaviors

- **Startup seeding → deploy-step seeding:** baseline seed (permission catalog, global template) becomes an idempotent script run in the migration pipeline and on local reset (M-11).
- **In-memory anything → durable state:** JWT verification uses supabase-js `auth.getClaims()` against the project JWKS (asymmetric signing keys per A-10); the JWKS cache is a performance cache only, safe to refetch on a cold start; dashboard filter persistence stays client-side; alert badge state stays in `user_alert_views`.
- **Hangfire dashboard → `jobs:status` + tables** (A-15).
- **Streaming attachments → signed URLs** (A-7/Q-22) issued through the `StorageAdapter` (A-6).

### 9.5 Background jobs — Hangfire replacement (PRD §11, Appendix A)

Job infrastructure (new migrations, per Q-7): **Supabase Cron (`pg_cron`)** provides scheduled triggers — schedules are defined as `pg_cron` jobs in SQL migrations. Chosen invocation approach: **pg_cron → `pg_net` HTTP call to the secret-protected Vercel endpoints** (`/api/cron/{job}`, `/api/queue/drain`), so the shared TypeScript handler logic runs on Vercel; the endpoints are idempotent and tolerate duplicate/missed invocations. **Supabase Queues (`pgmq`)** provides the durable queue (queue `alert_reevaluation`; pgmq's own tables supply enqueue / read-with-visibility-timeout / delete-as-ack / archive-as-dead-letter semantics), superseding the previously planned app-owned `job_queue` table. A durable **`job_run`** history table is kept for observability/idempotency (id, job_name, trigger `cron|queue|manual`, environment `local|preview|staging|production`, correlation_id, started_at, finished_at, duration_ms, status `running|succeeded|failed`, error_message/class/stack, counts jsonb — e.g., per-tenant expired/created/resolved), plus optional `job_error`, `job_idempotency_key` for critical types. Required Postgres extensions: `pg_cron`, `pgmq`, `pg_net` — all available in hosted Supabase and the local Supabase stack, enabled via migrations.

## 13. Authentication, Authorization, and Tenant Boundaries

- **AuthN:** Supabase Auth (A-4). SPA: sign-in/session via `@supabase/supabase-js`; the Supabase access token (JWT) is sent as the bearer token (client-managed refresh). API: Supabase-issued access tokens verified server-side via `@supabase/supabase-js` `auth.getClaims()` against the project's asymmetric JWT signing keys/cached JWKS (local/offline verification — no per-request network call, cold-start tolerant; asymmetric signing keys are required on every project, since the legacy HS256 shared secret would force a network round-trip per verification — A-10). Only the token issuer/verification mechanism changes from the prior Keycloak design — Supabase Auth provides authentication + identity, not authorization. Intake: first-party hashed API keys mapped to `api_credentials` rows per the approved Q-19 scheme (tenant/broker derived server-side; broker-scoped credentials cannot be spoofed).
- **Tenant context:** `X-Tenant-Id` on tenant-scoped routes, verified against the caller's memberships or Internal grant; explicit tenant parameter threaded through the data layer (no browser trust, no ambient global); cross-tenant endpoints explicitly marked, Internal-permission-bound, and audited.
- **AuthZ:** per-route declarative permission requirements resolved against the ported effective-permission model (union of direct/role/group grants within tenant context; global grants cross-tenant only when explicitly global). Effective-permission calculation, tenant context (X-Tenant-Id), and server-side authorization are unchanged by the Supabase Auth switch: the app's own RBAC (roles/groups/permissions, per-tenant assignments) remains the authorization source of truth — no Supabase Auth metadata/claims are load-bearing for authorization. Visibility-breadth permissions enforced in query predicates. UI gating is convenience only; server enforcement is authoritative.
- **Sensitive operations** (corrections, reopen, credential regeneration, bulk reassign, pricing approve/reject, exports, template edits, cross-tenant access) each carry their own permission and audit entry.
- **Supabase Auth Admin API integration:** User Manager provisions/links/disables identities via the Supabase Auth Admin API (`lib/supabase`, server-only `SUPABASE_SERVICE_ROLE_KEY` from env config); the Supabase auth user id (uuid) is stored on the app user row (`auth_user_id` referencing `auth.users(id)`). API-credential lifecycle (issue/regenerate/disable) is handled by the Q-19 first-party key scheme, not Supabase Auth.
- **RLS (Q-10 RESOLVED — NOT adopted; human decision 2026-07-20):** Row-Level Security is not enabled on any application table, and no policies are created. Server-side application authorization is the **sole** control: tenant-context middleware plus repository-level tenant predicates, integration-tested per endpoint (N-01). The Data API remains locked down by **grants** rather than policies — `anon`/`authenticated` hold no DML on `public` tables, so the browser-exposed anon key cannot read tenant data; this is pinned by regression tests (T-014) because it is now the only database-level protection and a stray `GRANT SELECT` in a future migration would silently remove it.

## 16. Security Considerations

- Zero trust at all boundaries; every input validated server-side; the SPA treated as hostile; no client-supplied tenant/user/role/permission trusted without verification.
- Secrets — static tier (A-5/Q-5): static server-only platform secrets — at minimum `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_DATABASE_URL`/`SUPABASE_DIRECT_DATABASE_URL`, `CRON_SECRET`/`INTERNAL_JOB_SECRET` (protecting the pg_net-invoked cron/queue-drain endpoints), and any API-key signing/pepper secret from the Q-19 scheme (`SUPABASE_JWT_SECRET` is not in the catalog — not required under A-10's asymmetric-key `getClaims()` verification) — are stored as **Vercel Sensitive Environment Variables** per environment (write-only, encrypted at rest, unreadable after set) and never reach the client bundle; browser-safe values (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` per M-20a) are unchanged — ordinary (non-sensitive) env vars; the typed config module is the sole access path; `.env*`/`.vercel` git-ignored; no secrets committed — local git-ignored `.env.local` holds local-only development values (the local-stack keys printed by `supabase start`), never real keys (A-5/Q-5).
- Secrets — tenant-scoped tier (A-5/Q-5; implementation deferred per Q-23): dynamic tenant-scoped secrets (tenant integration credentials, per-tenant outbound API keys, OAuth refresh tokens, integration secrets — all consumers are future scope) are designated for **Supabase Vault** (`vault` schema), encrypted at rest inside Postgres; when implemented, decryption is server-side only, under least privilege, exclusively through the server-side secrets module; tenant isolation is enforced on every read (a tenant's secrets are never readable in another tenant's context); access to tenant secrets is auditable; Vault-tier secrets never appear in the client bundle or in logs. **Nothing is built in this migration** (Q-23: no MVP consumer — documented pattern only). The Q-19 intake API keys are excluded from this tier: they are verify-only salted hashes in `api_credentials`, never retrievable, and are not stored in Supabase Vault.
- Supabase key discipline: the anon key is browser-exposed for Supabase **Auth** only (A-4) — the SPA's data path remains exclusively `/api/v1`, with no browser access to the Supabase Data API; because the anon key now ships to the browser, the database must not expose tenant data to the `anon`/`authenticated` PostgREST roles — enforced by **withholding grants** (those roles hold no `SELECT/INSERT/UPDATE/DELETE` on any `public` table), not by RLS policies, which are not adopted per Q-10. This grant lockdown is the only database-level protection of tenant data and is therefore pinned by regression tests (T-014). Service-role usage confined to server code.
- Cron/queue-drain endpoints protected by `CRON_SECRET`/`INTERNAL_JOB_SECRET` (they are invoked by `pg_cron` via `pg_net`, never publicly); queue consumers validate system authorization and tenant context per message.
- Attachment hardening preserved: content-type allow-list + extension check, per-tenant size cap enforced server-side before signing, private bucket only (no public bucket; storage access is service-role/server-only through the `StorageAdapter`, signed access exclusively), tenant-prefixed keys, short-lived signed URLs, `Content-Disposition: attachment` semantics on download, audit on add/remove. (Magic-number verification moves to a post-upload confirm step or is documented as a known change if infeasible without streaming — flag during implementation, do not drop silently.)
- Injection/XSS: parameterized SQL only; React default escaping; CSV formula-injection guarding (`'` prefix on `=+-@`).
- Account enumeration prevention preserved (generic login failure, uniform reset confirmation) — relies on Supabase Auth (GoTrue) response semantics plus the SPA's generic error rendering, and is verified during e2e adaptation.
- Transport/headers: HTTPS enforced by platform; security headers set in responses/`vercel.json`; CORS restricted to the SPA origin (same-project deployment makes this same-origin by default).
- Rate limiting per A-20/Q-17.
- Auditable admin/cross-tenant operations per P-13; authorization tests are first-class deliverables (§17).

## 20. Risks

- **R-1 Vercel body-size limit (~4.5 MB)** breaks streamed attachments (10 MB cap) and could truncate large synchronous exports. Mitigations: signed-URL flow (A-7/Q-22); documented export limit with queued-export scale path (Q-18). Highest-impact known constraint.
- **R-2 Platform job-scheduling constraints:** largely retired by Q-7 — Vercel Cron plan limits and Vercel Queues availability are no longer dependencies; scheduling and queuing run on Supabase (`pg_cron`/`pgmq`), already part of the adopted platform, with no sub-daily-schedule restriction. Residual risk: the `pg_net` HTTP hop from the database to the Vercel endpoints delivers asynchronously (timeouts/failures surface out-of-band). Mitigation: idempotent secret-protected endpoints, `job_run` visibility of missed/failed runs, schedule-driven self-healing, and the local worker/scripts path.
- **R-3 Transaction-pooler incompatibilities** (no session state, no named prepared statements, advisory-lock caveats). Mitigation: A-8 driver configuration; `SELECT … FOR UPDATE` sequence allocation stays inside single transactions (compatible); integration tests run through a pooler-equivalent path.
- **R-4 Auth coupled to the Supabase platform.** The former external-hosted-auth risk (Clerk: no offline identity stack, plan-gated features) is largely removed by the Q-4 reversal — Supabase Auth runs inside the platform this migration already depends on and works fully offline in the local Docker stack. What remains: authentication availability is now tied to the same Supabase project as the database (one platform incident affects both), the browser-exposed anon key requires the Data-API lockdown noted in §16, and switching IdPs again would change the login/e2e surface (P-01 sign-in page, Q-21 test strategy) and drop the ported replacements for Keycloak-era behavior (themed login pages, client-credentials intake tokens — replaced per P-01/Q-19, behavior changes to verify, not straight ports). Mitigations: Q-19/Q-21 both resolved (first-party API keys — no platform-feature dependency — approved for intake; e2e auth strategy approved); login flow isolated behind the SPA auth layer.
- **R-5 Loss of EF global query filters:** tenant predicates are now per-query discipline, and with RLS not adopted (Q-10) there is no database-level net beneath them — this raises R-5 from moderate to the **highest-consequence residual risk** in the migration, since a single forgotten predicate is a cross-tenant leak. Mitigation: mandatory per-endpoint tenant-isolation integration tests (N-01) and central query helpers, both now load-bearing rather than supplementary.
- **R-6 Function timeout vs sweep growth:** alert/expiry sweeps must stay within `maxDuration` as tenants grow. Mitigation: tenant batching now; per-tenant queue dispatch documented as the scale path (§9.5 Job 3).
- **R-7 Behavioral drift during port:** 27 endpoint files, a workflow matrix, and five dashboards leave room for subtle regressions. Mitigation: porting inventory (§9.1), metric-fixture sharing, e2e suite as gate (A-17), metric parity check (§18).
- **R-8 Magic-number/file-content validation** weakens under direct-to-storage uploads (see §16). Mitigation: post-upload verification step or explicit accepted-risk sign-off.
- **R-9 Seed-scale performance assumptions:** dashboard SQL re-written for `pg` may perform differently through the pooler. Mitigation: N-04 targets tested at seed volume; indexes carried over.
- **R-10 Reversal of prior platform decisions** (Vault, MinIO/S3 adapter, Liquibase) without explicit sign-off would violate governance. Mitigation: the HashiCorp Vault reversal is human-approved (Q-5 resolved: two-tier replacement — Vercel Sensitive Environment Variables for static/platform secrets + Supabase Vault for dynamic tenant-scoped secrets) and the MinIO/S3 reversal is human-approved with the adapter seam preserved (Q-6 resolved: Supabase Storage behind the swappable `StorageAdapter`); the Liquibase retirement is also human-approved (Q-3 resolved: fully retired, not retained even as a SQL runner). No unapproved reversals remain.
